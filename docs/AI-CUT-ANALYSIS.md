# AI 2세대 설계: 방송 내용과 채팅으로 근거를 추적해 편집 구간을 확정하는 컷 분석

작성: 2026-10-17 · 개정: 2026-10-18 (6-B 완료 기록: 자막 파일, 치지직 음성 받기, whisper.cpp, 설정) · 2026-10-22 (입력 v4: 탐지기의 반응과 채팅 곡선, 반응 우선 채팅 선택, 다시 분석 뒤 결과가 같은 순간을 따라감) · 상태: **확정** (결정 기록은 11절). 요약과 단계는 `docs/REDESIGN.md` 6.6절·12절에 있고, 자세한 규칙은 이 문서를 따릅니다.

> 출발점: 사용자가 전달한 제안서("더 많은 장면을 추천하는 AI보다, 반응의 근거를 추적하고 이해 가능한 편집 구간을 확정하는 AI"). 제안서는 공개 `main`의 옛 Python 구조 기준이라 현재 Go 구조에 맞춰 옮겼고, 2026-10-17 사용자 결정으로 **분석의 주 자료를 채팅에서 "방송 내용(방송자가 한 말·화면·소리) + 채팅"으로 바꿨습니다.** 방송 내용의 인식(음성 인식·소리 분류·화면 글자)은 이 컴퓨터의 로컬 모델이 하고, 인식 결과를 읽고 판단하는 분석은 지금처럼 사용자가 고른 AI 제공자가 합니다.

## 0. 한 문단 요약

기존 탐지기(`internal/detect`)는 **채팅으로 반응이 몰린 곳을 찾는 일**을 계속 맡습니다. 그 뒤에 새로 두는 **컷 분석**은 (1) 방송 음성을 로컬에서 글로 바꿔 두고(발언), 가능하면 소리 이벤트(웃음·비명)와 화면 글자도 로컬에서 뽑아 둔 뒤, (2) 후보 하나를 받아 `원인 후보 비교 → 부족한 맥락을 발언·채팅에서 검색 → 필수 맥락 선택과 경계 후보 3개 → 발언 경계로 시각 보정 → 클립만 보는 검수 → 원본과 비교하는 검수` 순서로 진행하고, (3) 결과를 **근거 ID가 붙은 컷 계획**으로 저장합니다. 모델은 밀리초를 지어내지 않고 근거 ID(발언·채팅)로 경계를 말합니다. 방송 내용을 받아 인식하는 일은 모두 이 컴퓨터 안에서 끝나고, 외부로 나가는 것은 사용자가 확인한 인식 결과(글)와 채팅뿐입니다. 지금의 "AI 검토"(장면 설명)는 가벼운 길로 남깁니다.

| 조각 결과를 합칠 뿐 사건 의존을 추적하지 않음 | `app.runAI` | 후보 단위 상태 기계(3.1절), 중간 상태 저장 |

### 1.2 editnest(참고용 `~/Desktop/editnest-main`)에서 가져올 것과 아닌 것

editnest는 NAS용 편집 준비 웹 앱(Python 표준 라이브러리 서버 + Rust `cutter`)입니다. 확인한 기능과 이 설계와의 관계:

| editnest 기능 | 내용 | MomentForge에서 |
|---|---|---|
| 무손실 구간 자르기(`cutter`, FilmCraft ISO BMFF) | MP4를 재인코딩 없이 키프레임 기준으로 자르고, 여러 구간을 하나로 이어 붙임. 48개 사례 검증(`cutter/REPORT.md`) | **컷 계획의 출력을 받는 쪽**. 컷 계획의 `selected_spans`를 editnest가 읽는 형식(CSV·EDL·FCPXML·OTIO)으로 내보내면 실제 파일 자르기는 editnest가 함. MomentForge가 자르기를 다시 만들지 않음 |
| 자막·대본(`captions`) | SRT·VTT·SCC·MCC·STL·TTML 읽기, 대사를 눌러 이동, 구간 만들기 | MomentForge가 만든 **전사를 SRT·VTT로 내보내면** editnest 대본 탭에서 그대로 씀 |
| 파형·무음·음량(`audio-dsp`) | AAC 디코드, 무음 나누기, LUFS | 시각 보정(4.4절)의 "문장 중간 피하기"에 무음 정보가 쓸모 있음. 2세대 뒤에 같은 방식(AAC 디코드 → 무음 구간)을 검토 |
| 영상 받기 | **유튜브만**, FrameNest(`yt-dlp`)에 요청 | 치지직 다시보기 받기는 editnest에 없음. MomentForge가 자체 HLS 받기(2.3절)를 가짐 |
| 음성 인식 | **없음**(N100에서 느려 뺌, 자막 파일로 대신) | MomentForge는 Apple Silicon 로컬 인식을 전제로 넣음(2.2절) |

즉 역할을 나눕니다: **MomentForge = 반응 찾기 · 방송 내용 인식 · 근거 추적 · 컷 계획**, **editnest = 영상 파일 자르기 · 이어 붙이기 · 편집 프로그램 내보내기**. 두 앱의 접점은 파일 형식(컷 CSV/EDL/FCPXML, SRT/VTT)입니다.

## 2. 자료: 방송 내용을 로컬에서 인식해 근거로 쌓기

### 2.1 근거 종류

모든 근거는 `종류:ID` 형식의 ref로 가리키고, 원본 시각(ms)과 함께 저장합니다. AI가 만든 요약은 근거가 아니라 **가설**로 따로 둡니다(제안서 3절: 관측·발언·시청자 해석·AI 가설을 분리).

| ref | 내용 | 어디서 | 단계 |
|---|---|---|---|
| `chat:<id>` | 시청자 채팅 원문, 시각, 가명 작성자 | 수집(있음) | 1차 |
| `comment:<id>` | 영상 댓글의 시각 추천 | 수집(있음) | 1차 |
| `utt:<id>` | **방송 발언**: 글, 시작·끝 시각, 화자(`방송자`·`게스트 1`…), 인식 신뢰도, 엔진·모델 버전 | 로컬 음성 인식(2.2절) 또는 사용자가 넣은 자막 파일 | **1차** |
| `sound:<id>` | 웃음·비명·박수·환호·알림음 구간 | 로컬 소리 분류(2.4절) | 확인 뒤 |
| `obs:<id>` | 화면 글자(게임 오버, 점수, 자막, 후원 문구 등)와 장면 전환 시각 | 로컬 화면 인식(2.4절) | 확인 뒤 |
| `gap:<id>` | 수집 공백·시간 오차(채팅과 영상 시간축 대응) | 수집(있음) | 1차 |

### 2.2 음성 인식(ASR): 로컬 엔진

사용자 결정: 인식은 로컬, 분석은 AI 제공자. 이 Mac(Apple M4, 16GB, macOS 27, Homebrew·ffmpeg·whisper 없음, Xcode 명령줄 도구 있음) 기준으로 두 엔진을 둡니다. 엔진은 `internal/asr` 패키지의 인터페이스로 두고 `cmd/momentforge`에서 등록합니다(제공자와 같은 등록 방식).

```go
// internal/asr (domain만 import)
type Engine interface {
    ID() string; Name() string
    Ready(ctx) (ok bool, how string)                 // 쓸 수 있는지와 준비 방법
    Transcribe(ctx, audio AudioFile, opts Options, progress func(Progress)) ([]domain.Utterance, error)
}
```

| 엔진 | 방식 | 장점 | 확인할 것 |
|---|---|---|---|
| **`apple-speech`** (macOS 26 이상) | Apple Speech 프레임워크의 `SpeechAnalyzer`/`SpeechTranscriber`를 쓰는 **작은 Swift 도우미 실행파일**을 `momentforge` 안에 embed해 두고 첫 사용 때 데이터 폴더 `runtime/`에 꺼내 실행. 한국어 모델은 OS가 받아 관리(앱이 모델을 받지 않음) | 설치 없음, Neural Engine, 모델 관리 불필요. 발언 단위 시각이 나옴 | 한국어(`ko-KR`)가 `supportedLocales`에 있는지는 **이 Mac에서 실제로 확인**해야 함(출시 언어 목록에 한국어가 있다는 2차 자료만 있고 베타에서 목록이 틀린 사례가 보고됨). 방송 음성(잡음·웃음·음악 겹침)에서의 품질 |
| **`whispercpp`** (모든 OS, 2026-10-18 구현: `internal/asr/whisper`) | 사용자가 설치한 `whisper-cli`(whisper.cpp)와 모델 파일의 **전체 경로를 설정에서 지정**(자동 탐색·자동 다운로드 없음). 모델은 `large-v3-turbo`(약 1.5GB) 또는 `large-v3-turbo-q5_0`(약 550MB)을 사용자가 받아 둠. 입력이 WAV가 아니면 ffmpeg(있을 때) 또는 macOS 내장 `afconvert`로 16kHz WAV를 만들어 넘김 | 플랫폼 공통, 한국어 다국어 모델 | 설치 부담(이 Mac에는 Homebrew도 없음). 한국어 정확도 수치는 직접 재야 함. 입력이 16kHz WAV라 디코드가 필요 |

추천: **macOS는 `apple-speech`를 기본으로, `whisper-cpp`는 선택**(11절 결정 9). Codex·OpenCode를 "설치된 CLI를 찾아 쓰는" 방식으로 넣은 것과 같은 원칙입니다. Swift 도우미는 `cmd/momentforge`가 아니라 별도 폴더(`tools/speech-helper/`, Swift Package)에서 빌드해 Go가 `embed`합니다. CGO 없이 유지됩니다(지금 빌드는 `CGO_ENABLED=0`).

**발언 나누기**(2026-10-21): 컷 분석은 발언의 시작·끝에서만 자르므로 발언 길이가 곧 경계 정밀도입니다. Apple 인식 결과 하나는 대개 10~20초(실제 방송 3시간에서 중앙값 9.6초, 최대 25.7초)라, 도우미가 결과마다 **낱말별 시각**(`audioTimeRange`, `words: [{s, e, t}]`)도 내보내고 `asr.Split`(`internal/asr/split.go`)이 결과를 나눕니다.

- 나누는 곳: 문장 끝(`.` `?` `!`) 뒤, 낱말 사이 쉼 0.6초 이상(`PauseMs`). 그래도 8초(`MaxMs`)보다 길면 가장 긴 쉼에서 다시 나눕니다(쉼이 같으면 가운데에 가까운 곳, 양쪽 1.5초 `MinMs` 이상을 우선). 값은 `asr.Options.Split`으로 바꿀 수 있고 비우면 `asr.DefaultSplit()`입니다.
- Apple은 낱말 사이 쉼을 빈틈이 아니라 **다음 낱말의 범위 앞부분**에 넣습니다(측정: 1.2초 이상인 낱말 17개 모두 앞이 무음, 소리는 끝에 몰림). 그래서 낱말 말소리를 끝에서 max(0.8초, 글자당 0.2초)로 보고, 그보다 긴 앞부분을 쉼으로 셉니다. 발언 시작도 그 말소리 시작입니다. 실제 방송에서 이렇게 줄인 시작 500곳을 소리 크기로 확인하니 97%는 실제 말소리가 그 뒤에 시작했고(중앙값 0.56초 뒤), 0.3초 넘게 앞서 시작한 곳(앞 여유로도 잘리는 곳)은 2%였습니다.
- 결과(공개 다시보기 15723059, 3시간 1분, 인식 1분 57초): 발언 859개 → **2,092개**, 길이 중앙값 9.6초 → **3.3초**(p90 16.0 → 6.4초, 8초 초과 512개 → 0개). 후보 5(2:00:51~2:03:07)의 끝 발언 "과일 껌 할게요. 선생님들 네모스낵…"(9.6초)이 "과일 껌 할게요."(1.4초)와 다음 상품 발언으로 나뉘어, 끝을 약 8초 앞에 둘 수 있게 됨.
- 짧은 발언끼리는 붙어 있으므로 컷 분석의 앞뒤 여유가 이웃 발언에 들어가지 않게 했습니다(4.4절).
- whisper.cpp는 아직 세그먼트 그대로입니다(낱말 시각 출력은 남은 과제).

화자 구분: 1차는 하지 않고 모두 `방송자`로 둡니다(치지직 개인 방송 전제). 게스트가 섞이는 방송은 2차 과제이며, 사용자가 자막 파일을 넣을 때는 화자 이름을 **역할명으로 치환**해 저장합니다(원문 이름은 저장하지 않음).

### 2.3 음성 받기와 보관

치지직 다시보기의 공개 HLS는 이미 재생용으로 씁니다(`PlaybackSource`). 전사는 그 재생 목록에서 **가장 낮은 비트레이트 렌디션(오디오 전용이 있으면 그것)** 을 기존 예의 바른 HTTP 클라이언트로 내려받아 조각을 이어 붙인 fMP4/TS 파일로 저장한 뒤 엔진에 넘깁니다. `yt-dlp` 같은 외부 받기 도구는 쓰지 않습니다(의존성 추가, 치지직 로그인 필요 영상은 어차피 보류).

- **보관 정책**: 사용자 결정(10번) — 영상 MP4를 채팅과 함께 **세션 백업 묶음**(2.5절)으로 보관할 계획이므로, 전사용으로 따로 받은 음성은 전사가 끝나면 지웁니다. 백업 묶음이 있으면 그 MP4에서 음성을 다시 뽑아 재전사하고, 없으면 다시 받습니다. 음성만 따로 남기는 옵션은 두지 않습니다.
- 영상(화면)은 2.4절 화면 인식을 켤 때만, 프레임을 뽑는 동안만 받고 지웁니다. **영상 파일을 보관·재생·자르는 일은 editnest 몫**입니다.
- 받는 양과 시간은 작업 카드에 진행률로 보여 주고, 중단·이어받기는 채팅 수집과 같은 규칙입니다.
- 생방송은 수집 중에 같은 렌디션을 받아 10분 단위로 전사합니다(5단계, 8절). 방송이 끝난 뒤의 다시보기 전사와 결과 형식은 같습니다.

구현(2026-10-18, 8절 6-B ⑥): `platform.AudioSource`를 `chzzk.VODAudio`가 구현해 위 규칙대로 받고, 받은 파일은 데이터 폴더 `runtime/audio/`에 두었다가 전사가 끝나면(실패해도) 삭제합니다. 앱을 켤 때 그 폴더를 비웁니다.

확인할 것(6-D 조사 항목): 치지직 다시보기 HLS에 오디오 전용 렌디션이 있는지, 조각 컨테이너(fMP4·TS)와 엔진 입력의 호환(Apple 도우미는 AVFoundation으로 fMP4·m4a를 읽음, TS는 리먹스 필요; whisper-cli는 WAV라 도우미의 `decode` 하위 명령이나 ffmpeg가 필요). 이 확인이 끝나기 전까지 2.3절의 "받아서 바로 넘긴다"는 가정입니다.

확인 결과(2026-10-19, REDESIGN.md 15절): 오디오 전용 렌디션은 없고 모든 변형이 영상+음성이며, 조각은 `EXT-X-MAP` + `.m4v`의 fMP4입니다. 첫 조각은 약 2.06초에서 시작하므로, 음성 받기도 백업 묶음 영상과 같이 조각의 `tfdt`를 첫 조각 시작만큼 당겨 파일이 0초에서 시작하게 합니다(읽는 쪽이 첫 시각을 어떻게 다루든 발언 시각이 채팅과 같은 시간축). 가장 낮은 변형(144p)의 fMP4는 Apple 도우미(AVFoundation)가 읽는 형식이지만 실제 받기·전사는 사용자와 확인 대기이고, whisper-cli 입력 변환은 남은 과제입니다.

### 2.4 소리 이벤트와 화면 인식 (로컬 가능성 확인 뒤 결정)

사용자 결정: "로컬 모델로 되는지 확인해서, 되면 구현하고 안 되면 보류". 확인 순서와 기준:

| 종류 | 후보 | 확인 방법 | 넣는 기준 |
|---|---|---|---|
| 소리 이벤트 `sound:` | Apple SoundAnalysis의 내장 분류기(`SNClassifySoundRequest`, 웃음·비명·박수·환호 등 레이블 포함) — 같은 Swift 도우미에 하위 명령 추가 | 실제 다시보기 30분에서 웃음·비명 구간을 뽑아 사람이 들어 보고 정확도·누락 확인 | 정확도가 쓸 만하고 30분 처리가 몇 분 안이면 1차에 포함 |
| 화면 글자 `obs:` | Apple Vision 글자 인식(OCR)으로 장면 전환 시점의 프레임에서 글자 추출(게임 오버·점수·후원 문구). 범용 영상 설명 모델(VLM)은 16GB에서 느리고 환각이 있어 **글자 인식만** | 다시보기 30분에서 장면 전환 프레임 수·처리 시간·한국어 OCR 품질 확인 | 프레임 수가 수백 장 이내, 글자 품질이 쓸 만하면 2차 |
| 장면 설명(무엇이 일어났는지 문장으로) | 로컬 VLM | 보류. 환각이 근거로 섞이는 위험이 크고 속도가 느림 | 넣지 않음 |

모두 **근거(관측)와 가설을 분리**합니다. "GAME OVER 글자가 03:12:40 프레임에 있음"은 관측이고, "게임에 실패했다"는 가설입니다.

1차 측정(2026-10-19, REDESIGN.md 15절): 공개 다시보기 15723059(버튜버 방송, 배경 음악, 화면 채팅 오버레이)의 10:00~40:00을 360p로 받아 쟀습니다. 측정 도구는 저장소에 넣지 않은 일회용 Swift 프로그램이고, 좋으면 `tools/speech-helper`에 하위 명령으로 옮깁니다.

| 종류 | 속도 | 결과 | 잠정 판단 |
|---|---|---|---|
| 소리 (`SNClassifySoundRequest` v1, 1.5초 창) | 30분 5.7초 (약 320배) | 반응 레이블 창이 적고(웃음 22·헐떡임 40·외침 19·비명 2) 배경 음악이 70%. 신뢰도 0.5 이상 사건 22개 중 64% 뒤에 채팅 웃음이 왔지만 아무 구간도 47%라 차이가 작음. 후보 4개 중 2개 근처만 | 속도 충족, 정확도는 사용자가 들어 보고 결정. 쓰게 되면 웃음·비명·외침만 낮은 무게로 |
| 화면 글자 (2초 표본, 특징 거리 0.5 이상만 `VNRecognizeTextRequest`) | 900장 12.7초 | 장면 전환 6번. 읽은 글자는 화면 채팅 오버레이와 인터미션 화면이 대부분이라 채팅과 겹침. 360p에서도 큰 한글은 읽음 | 이 방송 유형에선 새 정보 없음. 게임 방송 하나를 더 재고 결정 |

측정 중 발견: 치지직 조각을 이어 붙인 파일을 AVFoundation이 1초만 읽던 문제(조각 안 movie fragment 순번 반복)를 고쳤습니다(REDESIGN.md 15절). 전사용 음성 받기도 같은 문제였습니다.

### 2.5 세션 백업 묶음 (영상 + 채팅 + 분석 결과)

사용자 계획: 영상 MP4를 채팅과 함께 백업. 나중에 앱이나 DB가 없어도 **그 폴더만으로 다시 편집하고 다시 분석할 수 있는 묶음**을 목표로 합니다. 위치는 데이터 폴더 `backups/<세션 ID>/`(설정에서 다른 폴더·NAS 경로로 변경). 모든 파일은 사람이 열어 볼 수 있는 형식이고, 안에 원본 ID·닉네임·API 키·salt는 없습니다.

| 파일 | 내용 | 왜 넣는가 |
|---|---|---|
| `manifest.json` | 묶음 버전, 만든 시각, 앱 버전, 세션 ID·제목·플랫폼·영상 ID·길이·수집 상태, 각 파일의 크기와 SHA-256, **시간축 대응**(아래), 포함 여부 표 | 무엇이 들어 있고 서로 어떻게 맞는지 한 파일로 확인 |
| `video.mp4` | 다시보기 전체를 HLS에서 받아 **재인코딩 없이** fMP4로 담은 파일(가능한 화질을 설정에서 선택, 기본 720p). 로그인·유료 영상은 받지 못하므로 그때는 빠짐 | 편집 원본. editnest가 바로 자름 |
| `video.json` | 렌디션, 코덱, 해상도, 조각 수, 받은 시각, 누락 조각(있으면 구간 목록) | 백업이 완전한지 확인 |
| `chat.jsonl` · `chat.txt` | 전체 채팅(지금 내보내기와 같은 형식), 가명 작성자 | 반응 근거 |
| `transcript.json` · `transcript.srt` · `transcript.vtt` | 발언 표 전체(ID·시각·화자 역할·신뢰도·엔진·모델) | 방송 내용 근거. SRT·VTT는 editnest 대본 탭용 |
| `observations.json` | 소리 이벤트·화면 글자(2.4절이 들어오면) | |
| `timeline.json` · `timeline.csv` | 통합 타임라인(자동 탐지·시청자 추천·AI 추천, 컷 계획 요약) | 후보 목록 |
| `analysis/<분석 ID>.json` | 규칙 분석 결과(창·후보·근거), 규칙 버전·파라미터 | 같은 채팅이면 같은 후보라는 재현성 |
| `comments.jsonl` | 영상 댓글 시각 추천(있으면) | |
| `cuts/<계획 ID>/plan.json` · `cuts.csv` · `cuts.edl` | 컷 계획 전체와 editnest·편집 프로그램용 구간 목록 | 편집 결과물 |
| `ai-runs/<실행 ID>.json` | 보낸 계획(지시문·보낸 발언·채팅 ID), 모델, 토큰·비용, `sent_log`. **키 없음** | 무엇을 보냈는지 나중에 확인 |
| `notes.md` | 사용자가 남긴 메모(`user_notes`)와 확정한 컷 목록을 읽기 쉬운 글로 | 사람이 바로 읽는 요약 |
| `README.txt` | 이 묶음이 무엇이고 어떻게 다시 불러오는지(한국어) | 몇 달 뒤의 자신을 위해 |

**시간축 대응**이 핵심입니다. 채팅·발언·컷의 시각은 모두 "영상 시작부터의 ms"이고, 받은 `video.mp4`의 0초가 플랫폼 영상의 0초와 같아야 합니다. HLS 첫 조각의 시작 시각이 0이 아닐 수 있으므로 `manifest.json`에 `video_offset_ms`(MP4 0초 = 영상 시각 몇 ms)와 확인 방법(첫 조각 PTS)을 적고, 수집 공백(`gaps`)도 함께 둡니다. editnest에서 EDL을 열 때 이 오프셋을 더하도록 `cuts.edl`은 **MP4 기준 시각**으로 쓰고 `cuts.csv`에는 두 시각을 모두 둡니다.

묶음 만들기는 작업 화면 **파일** 탭의 "백업 묶음 만들기"에서 시작하고(진행 카드, 중단·이어받기), 이미 있는 묶음은 바뀐 파일(새 컷 계획, 새 전사)만 갱신합니다. 불러오기(묶음 → 새 데이터 폴더)는 6-D 이후 과제로 두되, 형식은 처음부터 불러올 수 있게 고정 스키마와 버전을 둡니다. 영상 받기는 2.3절의 HLS 받기를 그대로 쓰며 재인코딩·자르기는 하지 않습니다(그 일은 editnest).

구현(2026-10-19, 6-D): 파일 탭 **백업 묶음** 칸의 "백업 묶음 만들기"(있으면 "갱신", 영상이 멈췄으면 "영상 이어받기"). 실제 파일은 위 표와 조금 다릅니다. 기존 내보내기 형식을 그대로 쓰려고 `chat-manifest.json`(수집 상태)을 더하고, 분석은 `analysis/<분석 ID>/` 폴더, 통합 타임라인은 `timeline/`, 댓글은 `comments/`, 대본은 최신 하나를 `transcript.*`로 둡니다. 영상은 `platform.VideoSource`(`chzzk.VODVideo`)가 설정의 화질 이하 변형을 골라 초기화 조각과 모든 조각을 이어 붙이고, 조각의 `tfdt`에서 첫 조각의 시작을 빼서 **MP4 0초 = 영상 0초**로 만듭니다(`video_offset_ms = 0`, 원래 시작은 `video.json`의 `original_first_pts_ms`). 받는 동안 `video.mp4.part`와 `video.json`에 이어받을 위치(조각 수, 바이트, 트랙별 이동량, 빠진 구간)를 남기고, 끝나면 SHA-256을 재서 `video.mp4`로 바꿉니다. NAS 백업 작업은 영상을 복사하지 않고 `video.ref`만 씁니다. 다시 만들면 바뀐 파일만 옮기고, 지난 manifest에 있던 이 앱의 파일만 지웁니다. 결정은 REDESIGN.md 15절(2026-10-19)에 있습니다.

### 2.5a NAS 백업 폴더 불러오기 (2026-10-18 확인·결정)

사용자의 NAS(`docker/chzzk-automation`)가 치지직 다시보기를 매일 자동 백업합니다. 2026-10-18에 `김꼬멍 new/26/10/`에서 확인한 구성은 방송 한 편당 네 파일입니다: `YY_MM_DD 제목.mp4`(원본 화질 리먹스, 예: 1080p60 H.264, 7시간 43분에 28.5GB), **`.m4a`(원본 AAC 음성만, 673MB)**, `.chat.jsonl`(한 줄에 하나: `t` 영상 기준 ms, `at` 실제 시각, `type` chat·donation·subscription·system, `status`, `uid`, `nick`, `role`, `msg`, 이모티콘 URL, 후원 `amount`·`anonymous`·`donation_type`, 구독 `months`·`tier`), `.chat.txt`(읽기용). 영상·음성 트랙은 0초에서 시작하고 채팅 `t`의 끝이 음성 길이와 같아 **시간축 보정이 필요 없습니다**(`video_offset_ms = 0`).

그래서 6-B의 첫 경로는 치지직에서 음성을 받는 것이 아니라 **NAS 백업 불러오기**입니다.

| 항목 | 규칙 |
|---|---|
| 접근 | SMB 마운트(`/Volumes/<공유>/…`). 앱은 경로 입력 칸과 최근 폴더 목록을 두고, 실제 파일인지와 확장자만 검사. editnest API나 자체 NAS 프로토콜은 두지 않음 |
| 불러오는 것 | 같은 이름의 `.chat.jsonl`(없으면 `.chat.txt`는 쓰지 않음: 시각 정밀도와 종류 정보가 부족)로 **새 세션**을 만들고, `.m4a`를 Mac으로 읽어 로컬 전사. `.mp4`는 읽지 않고 경로만 기억(백업 묶음의 `video_ref`, editnest가 자를 때 씀) |
| 가명화 | `uid`·`nick`은 세션별 salt로 가명 키를 만들고 원본은 저장하지 않음(채팅 수집과 같은 규칙). `uid`가 `anonymous`·`null`이면 가명도 비움. 이모티콘 URL은 저장하지 않고 코드(`{:이름:}`)만 둠 |
| 후원·구독 (사용자 결정 2026-10-18: **넣음**) | 채팅 표에 `kind`(chat·donation·subscription·system)와 `amount`(후원 원, 구독은 개월 수)를 더함(새 마이그레이션 `ALTER TABLE chat_events ADD COLUMN`). 재생 위치 채팅 카드에 💰·⭐ 태그와 금액으로 보이고, 컷 분석 근거에 `donation:`·`subscription:` ref로 들어가 "후원 반응" 원인을 가릴 수 있게 함. 내보내기 TXT·JSONL과 MCP에도 포함. **탐지 규칙에는 아직 쓰지 않음**(규칙 버전을 올리는 일이라 따로 결정). `status`가 `CBOTBLIND`(봇 차단)인 줄은 저장하되 표시에서 구분 |
| 세션 정보 | 제목·날짜는 파일 이름에서, 길이는 m4a에서. 치지직 `videoNo`는 파일에 없으므로 "치지직에서 열기"는 비워 두고, 뒤에 사용자가 주소를 붙여 넣으면 연결 |
| 중복 | 같은 폴더·같은 파일 이름을 다시 불러오면 기존 세션을 열고, 전사만 다시 할지 물음 |
| 치지직 직접 받기 | 백업이 없는 영상을 위한 **두 번째 경로**로 남김(2.3절). 구현 순서는 NAS 불러오기 → 자막 파일 → 치지직 받기 |

```text
① 읽기      후보 편집 구간 ± 60초의 발언과 채팅(반응 구간부터 고름), 최고점 통계, 탐지기가 잰 반응(구간·최고점·세기·두드러진 수)과
            5초 칸 채팅 곡선, 겹치는 다른 출처 후보, 그 구간의 소리 이벤트·화면 글자
② 원인 분석  원인 후보 여러 개(방송 사건 / 앞선 발언의 회수 / 시청자 농담 / 후원 / 미상)와 지지·반대 근거,
            반응 방향(방송→시청자 / 시청자→방송자→시청자), 해결되지 않은 질문, 검색 요청
③ 검색      서버가 요청을 실행(3.2절) → 결과를 붙여 ②로 (예산 안에서 반복)
④ 컷 계획   이야기 기원 / 현재 사건 시작 / 추천 시작, 필수·보강·제외 맥락, 결말 상태,
            경계 후보 3개(짧은 · 맥락 보존 · 전체 사건)를 **발언 ID**(없으면 채팅 ID)로
⑤ 시각 보정  서버가 근거 ID → 밀리초(4.4절)
⑥ 검수 1    선택 구간의 발언·채팅만 주고 "무엇을·조건·결과·'아까'는 무엇·왜 반응" 답하게 함
⑦ 검수 2    선택하지 않은 앞뒤와 과거 근거까지 주고 잘림·누락·다른 시도 혼합 확인
⑧ 저장      컷 계획 + 검수 보고 + 읽은 범위 + 미해결 질문 + 버전
```

검수가 실패하면 ④로 한 번 돌아가고(이유를 입력에 넣음), 두 번째도 실패하면 **"검수 실패"로 저장**하고 이유를 그대로 보여 줍니다.

⑥의 실패 기준(지시문 v2, 2026-10-19): 클립 근거 중 계획이 target을 설명하려고 기댄 것(첫 원인의 지지 근거, 필수 맥락, 이야기 기원, 사건 시작)에 `key: true`를 붙여 보냅니다. 과거를 가리키는 말은 key 근거에 있거나, 여러 작성자가 같은 과거를 가리키거나, 방송자의 답이 target의 일부일 때만 실패 사유(`gaps`)이고, key가 없는 시청자 한 사람의 곁가지 말은 `asides`(참고, 실패 사유 아님)로 받습니다. 질문과 답·말실수·농담처럼 원래 조건이 없는 사건의 "조건 없음"도 실패 사유가 아닙니다. 계기는 실제 다시보기 15723059 확인에서 곁가지 채팅("이미 써먹었죠") 때문에 후보 1이 재계획 뒤에도 검수 실패로 남은 것입니다(REDESIGN.md 15절).

지시문 v3(2026-10-21): `gaps`와 `asides`의 각 항목은 근거 ref 목록과 설명(`{refs, text}`)이고, 서버(`cut.ReclassifyClip`)가 ref를 보고 분류를 다시 정합니다. 모델의 글만으로 실패 여부가 갈리지 않게 하기 위해서입니다.

- 클립 안에 없는 ref는 버립니다.
- `asides` 항목이 key 근거를 가리키거나, 서로 다른 작성자 2명 이상의 채팅을 가리키면 `gaps`로 올립니다.
- `gaps` 항목이 key가 아닌 채팅만, 그것도 한 작성자의 것만 가리키면 `asides`로 내립니다. ref가 없거나 발언·작성자를 모르는 채팅을 가리키는 항목은 모델이 둔 자리에 둡니다.
- 남은 `gaps`가 없으면 통과입니다. 단, 모델이 `gaps` 없이 실패라고 한 경우는 실패로 둡니다.
- 옮긴 내역(`server_changes`)은 계획에 저장하고 결과 상자 "검수 답 보기"의 "서버가 바꾼 분류"와 MCP `mf_get_cut_plan`에서 보여 줍니다. 재계획에 넘기는 실패 사유에는 근거 ref를 붙입니다.
- v2 이전 계획의 문자열 항목은 ref 없는 항목으로 읽습니다.

엄격함 검사(개발용, `cmd/momentforge/cut_strict_test.go`): 통과한 계획에서 이야기 기원·필수 맥락 근거의 시간을 클립에서 잘라 내고 ⑥만 다시 보냅니다. 엄격한 검수라면 실패해야 하고, 여전히 통과하면 검수가 느슨하거나 그 맥락이 필요 없던 것입니다. 데모 "아까 약속" 사례(3:40 약속을 뺀 클립)는 실패해야 합니다. `TestCutStrictnessDemoProbe`는 보내지 않고 입력과 서버 재분류만 확인하며(느슨한 답이 "아까 벌칙"을 곁가지로 적어도 서버가 실패로 올림), 실제 제공자 확인은 환경 변수로만 켭니다.

```bash
MF_CUT_STRICT_PROVIDER=cliproxy MF_CUT_STRICT_MODEL=<모델> [MF_CUT_STRICT_DATA=<데이터 폴더>] [MF_CUT_STRICT_REPORT=<파일>] go test ./cmd/momentforge -run TestCutStrictness -v
```

데이터 폴더를 주면 그 안의 현재 통과 계획마다 요청 1회를 더 보냅니다(읽기 전용으로 엶). 클립 근거는 세션의 최신 대본과 저장된 채팅에서 구간 안의 것을 다시 읽으므로, 분석 때 보낸 근거보다 많을 수 있습니다.

입력 v4(파이프라인 4, 지시문 analyze v3·plan v2, 2026-10-22): 채팅만 보고는 반응이 어디서 오르고 잦아드는지 알기 어렵고, 채팅이 400건을 넘는 창에서는 시간순 앞의 400건만 보내 반응 자체가 잘리는 일이 있었습니다. 그래서 첫 입력을 이렇게 바꿨습니다.

- `candidates[].reaction`(규칙 후보만): 탐지기의 `start_ms`·`end_ms`(채팅이 반응한 구간), `peak_ms`(반응이 가장 몰린 시각), 전체 방송 분석이면 `strength`(strong·medium·weak)·`score`(그 시각대 평소와 다른 정도, z 척도)와 `measures` 최대 4개(`key`, 최고점 창에서 센 `observed`, 그 시각대 보통 값 `usual`, 창 길이 `window_s`; `repeat:` 낱말은 20자까지). 컷 계획의 `reaction.peak_ms`도 이제 클립 시작이 아니라 이 최고점입니다(시청자 댓글 후보는 댓글 시각).
- `curve`: 후보 클립(반응 구간과 합친 범위)을 5초 칸(10분을 넘으면 칸을 키워 120칸 이하)으로 나눠 칸마다 `chats`·`authors`·`reacting`(같은 칸에서 다른 작성자와 같은 반응 키(웃음·놀람·같은 말)를 보인 작성자, 탐지기와 같은 규칙과 정규화)을 세고, 앞뒤 10분의 칸 중앙값을 `usual_chats`·`usual_authors`로 붙입니다. 곡선은 보내지 못한 채팅까지 셉니다. 한 창에서 2만 건을 넘게 읽어야 하면 읽은 데까지만 세고 `partial`을 둡니다.
- 채팅 고르기: 창의 채팅(가린 채팅 제외)이 400건을 넘으면 후원·구독 알림 → `[반응 시작 − 60초, 반응 끝 + 30초)`의 채팅 전부 → 그 바깥을 가까운 쪽부터 채웁니다. 반응 구간만으로 넘치면 5초 칸마다 돌아가며 한 건씩 골라 오르내림이 남게 합니다. 남긴 수는 `chats_left_out`으로 알립니다.
- 플랫폼이 가린 채팅(봇 필터, `hidden`)은 컷 분석 근거(첫 입력·검색·엄격함 검사)에 넣지 않고, 후원·구독·시스템 알림은 `chat_kind`로 표시해 시청자의 말로 읽지 않게 합니다(금액은 보내지 않음).
- 새 필드는 모두 입력 JSON의 일부라 미리보기 "보낼 내용 전체"와 실행 기록(`plan_json`, `sent_log`의 바이트)에 그대로 들어갑니다.
- 1세대 장면 설명의 `statistics`에도 `reaction_start_ms`·`reaction_end_ms`·`peak_ms`와 (전체 방송 분석이면) `strength`·`score`를 더했습니다(검토 지시문 v4). 후보 크기가 커져 10KB 조각이 나뉘는 자리가 바뀔 수 있습니다.

같은 날 고친 실행 규칙:

- 재계획 때 계획과 검수 결과는 같은 시도의 것만 저장합니다. 구조 검사를 통과한 마지막 시도(그 시도의 두 검수와 실패 이유)를, 하나도 없으면 마지막 시도를 저장합니다. 이전에는 구조 검사에 걸린 재계획에 앞 시도의 검수 결과가 붙을 수 있었습니다.
- `CheckPlan`은 분석 근거·필수 맥락·보강 맥락 어디서든 읽지 않은 ref를 지어내면 재계획 사유로 삼습니다(이전에는 보강 맥락만 봄).
- 후보 하나의 단계가 실패해도(형식 오류, 거절, 재시도 뒤 서버 오류) 나머지 후보는 계속 분석하고, 실행을 `partial`로 끝내며 "후보 N개 중 M개를 분석하지 못했습니다. 00:04:25 후보: 이유"를 남깁니다. 사용자 중단, 요청·비용 한도, 키·권한·모델·프로그램 문제(`CREDENTIALS`, `AI_HTTP_401·403·404`, `AI_UNAVAILABLE`, `AI_FREE_TIER`)는 실행 전체를 멈춥니다.
- 검색 결과를 합칠 때와 "보내지 않기"로 뺄 때 미리보기의 근거 목록을 고치지 않고 새 목록을 만듭니다.

### 3.2 검색 도구 (서버가 실행)

모델은 ②의 출력에 검색 요청 목록을 적고, 서버가 실행해 다음 요청에 결과를 넣습니다. 도구는 `app`(`internal/app/ai_tools.go`)에 두고 MCP 도구와 같은 저장소 조회를 씁니다. 발언이 있으면 **발언을 먼저, 채팅을 보조로** 돌려줍니다.

| 요청 | 인자 | 서버 동작 | 상한 |
|---|---|---|---|
| `search` | `query`(필수), `before_ms`(기본: 현재 사건 시작), `in`: `utterances|chats|both`(기본 both) | 발언 FTS/부분 일치 + 채팅 부분 일치. 약속·고유 표현 찾기. `before_ms`에 **가까운 것부터** 고르고 시간순으로 돌려줌. `both`에서 발언이 30건을 채워도 채팅 10건 자리를 남김(2026-10-22). 가린 채팅 제외 | 결과 30건, 질의 40자 |
| `read_around` | `at_ms`, `window_s`(≤ 300) | 그 시각 앞뒤의 발언과 채팅을 시간순으로 섞어서 | 발언 120건 + 채팅 200건 (발언은 2026-10-21 나누기 뒤 60 → 120: 평균 약 5초 간격이라 300초 창이 60건을 넘음) |
| `read_range` | `from_ms`, `to_ms`(≤ 10분) | 구간의 발언과 채팅 | 같음 |
| `events` | `from_ms`, `to_ms` | 소리 이벤트·화면 글자·장면 전환(있을 때) | 200건 |
| `activity` | `from_ms`, `to_ms`, `bucket_s` | 채팅 활동량(반응이 몰린 곳 훑기) | 500칸 |
| `list_threads` | `before_ms` | 이야기 색인(6-E 이후) | 50건 |

임베딩(의미) 검색은 1차에 넣지 않습니다(로컬 임베딩 모델 추가 또는 전체 전송이 필요). 대신 모델이 표현을 바꿔 가며 `search`를 여러 번 하고, 못 찾으면 `activity`→`read_around`로 훑게 합니다.

**검색 종료 조건**: 필수 질문 해결, 원본 읽음, 같은 이야기·시도 확인, 반대 근거 검토. 예산을 다 쓰면 "검색 범위 안에서 확인하지 못함"으로 끝내고 `searched_ranges`에 남깁니다.

**예산**(기본값, 설정 화면 "AI 검토 › 컷 분석의 검색 예산"에서 변경): 후보당 검색 단계 4회(0이면 검색 없음, 최대 10), 단계당 요청 6개, 검색으로 추가되는 글 80KB(발언+채팅, 최대 1024KB). 후보당 요청 상한은 기본 4단계 + 재계획 3회 + 검색 단계 수 = **11회**(구현 기록: 설계 초안의 "8회"는 검색 단계를 포함하면 재계획 여유가 없어 이렇게 정함). 비용 한도는 기존과 같습니다. 검색이 새 근거를 하나도 못 찾으면 그 자리에서 검색을 끝내고(같은 요청은 다시 실행하지 않음), 모델이 더 찾고 싶어도 단계가 끝나면 `search_budget.exhausted`로 남깁니다.

### 3.3 제공자와 요청 형식

기존 `Review(chunk)`는 한 번 보내고 받는 형식입니다. 단계별 입력을 위해 선택 인터페이스를 더합니다.

```go
type StepProvider interface {
    Step(ctx context.Context, key, model string, step StepRequest) (json.RawMessage, Usage, error)
}
```

- 단계별 지시문·스키마·검증은 `internal/ai/cut/`(순수, `ai`·`domain`만 import). 지시문은 고정이라 프롬프트 캐싱이 됩니다.
- 사용자 결정(4번): **모든 제공자**가 구현합니다. Codex·OpenCode CLI 하네스는 요청마다 프로세스를 띄우므로 미리보기에 "느릴 수 있음"을 표시합니다.
- Claude의 네이티브 도구 사용은 선택 최적화로 뒤에 둡니다(구현 시 claude-api 스킬 확인). 배치 전송은 2세대에 쓰지 않습니다.

### 4.3 검증 (`ai/cut.Validate*`)

| 검사 | 규칙 | 실패 시 |
|---|---|---|
| 형식 | 스키마대로, 모든 ref가 `utt:`·`chat:`·`comment:`·`sound:`·`obs:` 중 하나 | 응답 거부(`AI_FORMAT`) |
| 읽은 근거 | 모든 ref가 **이 실행에서 서버가 보낸 적 있는 ID** | 그 항목 제거, `rejected` 집계 |
| 포함 규칙 | `required_context_refs ⊆ analysis_evidence_refs`, 모든 필수 맥락이 `selected_spans` 안, `start_ref` 시각 ≤ `end_ref` 시각, 구간 겹침 없음 | 계획 단계로 1회 되돌림, 그래도 실패면 "검수 실패" |
| 길이 | 구간 합 ≤ 10분, 구간 수 ≤ 4 | 같음 |

근거가 주장을 뒷받침하는지는 ⑥⑦ 검수가 따로 봅니다. 검수 모델은 ④와 다른 요청이고 ⑥에는 선택 구간의 원본만 넣습니다.

### 4.4 시각 보정 (서버)

- 발언 ref면 **발언의 시작·끝 시각**을 씁니다(문장 중간을 피함). 시작은 발언 시작 − 0.3초, 끝은 발언 끝 + 0.5초(첫·끝 음절이 잘리지 않게).
- 채팅 ref면 채팅 시각 − 반응 지연(6초), 끝은 + 3초. 그 시각이 발언 중간이면 그 발언의 경계로 옮깁니다(시작은 그 발언 시작 − 0.3초, 끝은 그 발언 끝 + 0.5초, 최대 10초).
- 앞뒤 여유(0.3초·0.5초)는 **이웃 발언에 들어가지 않습니다**: 앞 발언 끝보다 앞으로, 다음 발언 시작보다 뒤로 가지 않습니다. 한 인식 결과를 나눈 짧은 발언(2.2절)은 서로 붙어 있거나 수백 ms만 떨어져 있어, 그대로 더하면 다음 발언의 첫 음절이 들어가기 때문입니다(2026-10-21).
- 근거 버튼(▶)의 시각은 따로 셉니다: 발언은 발언 시작 그대로, 채팅·댓글은 − 6초.
- 옮긴 모든 시각(발언 앞뒤 여유, 채팅 지연, 발언 경계로 당김, 구간 합침, 영상 끝 맞춤)은 `boundary_decisions.adjustments`에 `{ref, from_ms, to_ms, why}`로 남깁니다.
- 소리 이벤트(웃음)가 끝 근처에 있으면 그 끝까지 포함합니다(웃음 중간에서 끊지 않음).
- 연속 구간 사이 20초 미만이면 합치고, 영상 밖·수집 공백은 잘라 `adjustments`에 적습니다.
- 무음 다듬기는 editnest의 무음 분석을 쓰거나 뒤에 같은 방식을 넣습니다.

### 4.5 통합 타임라인과 내보내기

- `TimelineItem`에 `spans[]`, `cutPlanId`, `kind: "cut"`을 더합니다.
- **다시 분석 뒤에도 같은 순간에**(2026-10-22, 마이그레이션 `0012_ai_moments.sql`): 규칙 후보 ID는 한 분석 안의 순번(m0001…, 시간순)이라 "다시 분석"하면 같은 ID가 다른 장면을 가리킬 수 있습니다. 그래서 AI 실행(`ai_runs.analysis_id`)과 컷 계획(`ai_cut_plans.analysis_id`)에 후보 ID가 속한 분석을 남기고, 통합 타임라인을 만들 때(`app.momentHosts.hostsFor`) 그 분석이 지금 분석이면 ID를 그대로 쓰고, 아니면 시간으로 지금 후보를 찾습니다: 결과의 범위(장면 설명은 추천 구간, 컷 계획은 `candidate_clip`, 없으면 setup을 뺀 고른 구간)와 겹치는 길이가 가장 긴 지금 규칙 후보(최소 5초 또는 짧은 쪽 길이의 절반, 같으면 원래 ID → 최고점을 담은 후보 → 앞선 후보). 원래 ID는 그 후보가 여전히 그만큼 겹칠 때만 남습니다. 겹치는 후보가 없으면 붙이지 않고 따로 한 줄로 둡니다. 시청자 댓글 후보 ID는 바꾸지 않습니다. 컷 상자의 `candidateIds`는 지금 후보이고, 바뀌었으면 `analyzedCandidateIds`에 분석했던 ID가 남습니다(MCP `mf_list_cut_plans`·`mf_get_cut_plan`도 같음). 0012 이전 실행은 그 실행이 시작될 때 가장 새 분석으로 채웁니다.
- **버전 계보(lineage)**: 한 순간의 계획 버전들은 후보 ID 문자열 대신 `ai_cut_plans.lineage`로 묶습니다(새 계보는 첫 계획의 ID, 0012 이전 계획은 후보 ID 그대로). 메모 모으기(`cutNotes`), 확정 하나만 두기(`ConfirmCut`), 확정본 유지 표시(`keptVersion`), 현재 계획(`CurrentCutPlans`)·확정본(`ConfirmedCutPlans`)이 모두 계보 단위입니다. 미리보기는 고른 후보 아래에 지금 보이는 가장 새 계획의 계보를 이어 새 버전을 만들고(번호가 바뀐 뒤에도), 화면이 `AIPreviewRequest.ContinuePlans`(후보 ID → 계획 ID)로 이어 갈 계획을 직접 지정할 수도 있습니다. 번호를 물려받은 다른 장면은 새 계보로 시작해 앞선 메모가 섞이지 않습니다.
- 내보내기 `exports/<세션>/cuts/<계획 ID>/`: `plan.json`(위 구조), `cuts.csv`(계획 ID, 순서, 시작, 끝, 역할, 이유), **`cuts.edl`**(editnest·편집 프로그램용). 전사는 `exports/<세션>/transcript/<id>.srt`·`.vtt`.
- 사용자 결정(5번): **분리 구간을 1차에 포함**(데이터 구조, 타임라인 표시, 이어 재생, 내보내기).
- 확정본(6-D): `exports/<세션>/cuts/confirmed.edl`(CMX 3600, 확정한 계획의 구간을 시간순으로 이어 붙인 가편집, `* FROM CLIP NAME`은 영상 파일 이름 또는 작업 제목, `* COMMENT`는 반응 대상과 역할), `confirmed.csv`(계획 ID, 버전, 경계 후보, 순서, 역할, 시작, 끝, 반응 대상, 상태), `confirmed.editnest.json`(editnest "타임라인 메모"의 JSON 형식: `segments[{id, start, end, title, note, tag}]` 초 단위, 영상 파일이 있으면 `videoName`). 확정이 하나도 없으면 세 파일을 지웁니다. 각 계획 폴더의 `cuts.csv`·`cuts.edl`도 확정한 경계 후보로 다시 씁니다.

## 5. 미리보기와 전송 범위

2세대에서 외부로 나가는 것은 **발언 글, 채팅, 소리·화면 관측 레이블**입니다. 음성·영상 자체는 나가지 않습니다. 발언은 방송자가 실제로 한 말이라 채팅보다 민감하므로 PRIVACY.md에 "AI 컷 분석은 방송 음성을 글로 바꾼 발언을 제공자에 보냄"을 명시하고, 처음 켤 때 한 번 안내합니다.

단계별 검색은 보낼 내용을 미리 전부 보여 줄 수 없습니다(어디를 찾을지는 첫 구간을 읽은 뒤 모델이 정함). 비교:

| 방식 | 사용자가 확인하는 것 | 장점 | 단점 |
|---|---|---|---|
| A. 상한에 한 번 동의 | 처음 보낼 내용 전체 + "이 방송의 발언·채팅을 최대 80KB·요청 8회까지 더 보냄" | 흐름이 끊기지 않음 | 추가로 보낸 것은 끝난 뒤 기록으로 봄 |
| B. 검색마다 확인 | 검색 결과를 보낼 때마다 멈춤 | 보내기 전에 전부 봄 | 후보 하나에 3~5번 멈춤 |
| C. 검색 없음 | 고정 입력만 | 단순 | 과거 맥락을 못 찾음 |

**추천: A 기본, B 옵션.** 상한은 비용·시간·"미리보기 숫자가 거짓이 되지 않게"를 위한 멈춤 장치이며 설정에서 올릴 수 있습니다. 실행 기록에 `sent_log`(단계, 도구 요청, 보낸 발언·채팅 ID와 바이트)를 남기고 "보낸 내용 전체"에서 단계별로 펼쳐 봅니다. 검색은 그 세션 안에서만 합니다. (11절 결정 1)

## 9. 평가

같은 후보 묶음에 네 방식을 비교합니다: `탐지기 앞뒤 여유만` → `1세대 고정 범위 설명` → `발언+검색 포함 컷 분석` → `검수 포함 컷 분석`. 지표는 제안서대로(원인 연결 정확도, 과거 맥락 검색 성공률, 필수 맥락 보존율, 결말 누락·왜곡률, 경계 수정량, 독립적 이해도, 처리율·오류율)이고, 전사가 있는 경우와 채팅만인 경우를 **따로** 잽니다(전사의 기여를 보기 위해). 정답은 허용 시작·끝 범위 + 반드시 포함할 구간으로 적습니다. 정답 세트는 `e2e/cut-eval/`에 데모 사례(가짜 발언 포함)로 먼저, 사용자가 고른 실제 다시보기 2~3편으로 10건 이상 더합니다. 시험 사례: 후원과 사건이 겹침, 비슷한 도전 반복, 반어법, 전사에서 부정어 누락, 뒤늦은 정정, 수집 공백, 결말 없는 사건.

E2E 가짜 제공자는 결정적인 단계 응답을 내도록 확장합니다. E2E용 가짜 ASR 엔진은 데모 데이터의 발언을 그대로 돌려줍니다(외부 연결·모델 없음).

구현(2026-10-19): `internal/cuteval`과 `e2e/cut-eval/`(사례 형식과 실행법은 그 폴더의 README). 채점기는 저장된 결과만 읽어 탐지기 구간, 1세대 장면 설명, 컷 분석(AI 선택)과 짧게·맥락·전체를 같은 정답으로 채점하고 Markdown 보고서를 냅니다. 계획에는 검수 전 구간이 남지 않아 "검수 전/후" 대신 검수 결과 열을 둡니다. 데모 사례 1건이 들어 있고, 실제 사례는 사용자가 고른 방송에서 확정한 컷으로 초안을 만든 뒤 사람이 고쳐 더합니다(REDESIGN.md 15절).

- 새 패키지: `internal/ai/cut`(→ `ai`, `domain`), `internal/asr`(→ `domain`), `internal/asr/<엔진>`(→ `asr`, `domain`). `app`은 `asr` 루트만 import. `check_layers.py` 표와 `ALLOWED`에 추가.
